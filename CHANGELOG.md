## v1.10.2 - v1.10.2

*Released: 11/8/2026*

Version 1.10.2 - Correct language detection for ASS/SSA subtitles

**Fixes every .ass and .ssa subtitle being detected as English.**

Drop an MKV with multiple ASS subtitle tracks and all of them came back
English, no matter what language they actually were. A Crunchyroll release
with English, Latin American Spanish and Brazilian Portuguese tracks showed
English three times.

Reported against "Digimon Beatbreak S01E01 1080p CR WEB-DL AAC2.0
H.264-OldT.mkv", which has exactly that layout.

**What went wrong**

Language detection sends the first 5 KB of a subtitle to the server and asks
what language it is. The server samples roughly the first hundred lines of
what it receives.

For SubRip that is mostly dialogue, so it worked. For Advanced SubStation
Alpha it is not. An ASS file opens with a `[Script Info]` block and a
`[V4+ Styles]` section — about 1.6 KB before the first line of dialogue — and
every event after that carries a long ASCII prefix:

    Dialogue: 0,0:00:16.10,0:00:20.23,BottomCenter,,0,0,0,,{\i1}Hello{\i0}

Timecodes, style names and override tags are identical in every language, and
they outweighed the real text in the sample. The server ended up reporting the
header back to us:

    content_preview: "ScriptType: v4.00+ Collisions: Normal PlayResX: 640 ..."
    languages:       en=0.192, de=0.070, ru=0.063

That same answer came back for all three tracks, which is why they all read
English — the detector never saw a word of dialogue.

**The fix**

Detection now runs on dialogue text only. Headers, style definitions,
timecodes, override blocks, vector drawing commands and `Comment:` events
(translator notes, frequently English inside a non-English script) are left out
of the sample. The window read from disk grew to 4 MB so scripts with many
styles or an embedded font section still reach their dialogue.

The same three tracks now detect correctly:

| Track | Before | After |
|-------|--------|-------|
| English | en 19.2% | en 94.2% |
| Latin American Spanish | en 19.2% | es 99.6% |
| Brazilian Portuguese | en 19.2% | pt 99.7% |

SRT, VTT and MicroDVD get the same treatment, so indexes, timecodes and `<i>`
markup no longer dilute those samples either.

**Your files are not touched.** Stripping applies only to the copy sent for
detection. ASS and SSA subtitles upload exactly as they are, byte for byte —
nothing is converted to SRT.

Cached detection results from before this change are discarded rather than
served for the remainder of their 72-hour lifetime.

**Also in this release**

- 18 new tests, including a regression fixture built from the real tracks of
  the reported file.

## v1.10.1 - v1.10.1

*Released: 10/15/2026*

Version 1.10.1 - Encoding fix for link removal

**Fixes subtitle corruption in "Remove Links from Subtitles".**

If you used this option on a subtitle in any non-Latin script — Hindi, Russian,
Greek, Arabic, Chinese, Japanese, Korean — the saved file came out mojibake.
The damage was written into the uploaded file, not just the preview. Latin-script
subtitles were never affected.

Thanks to @vegatortoise for reporting it with the screenshots that pinned it down.

**What went wrong**

Edits are applied over a byte-exact view of the file so that subtitles in cp1250,
cp1251, Big5 and friends keep their original encoding. That view was built with
`TextDecoder('iso-8859-1')` — and in every browser and WebView, the ISO-8859-1
label is an alias for the windows-1252 decoder. Bytes 0x80-0x9F came back as
code points above U+00FF and were written out as the wrong byte: 0x87 became
`!`, 0x8B became `9`. That byte range appears throughout the UTF-8 encoding of
most non-Latin scripts, so the text was shredded.

The view is now built directly from the raw bytes, which is a true 1:1 mapping
everywhere.

**Verified across encodings**

Every encoding family now has a byte-for-byte test through the full sanitizer:
UTF-8 Devanagari, CP1251 and KOI8-R Cyrillic, CP1250 Czech, ISO-8859-7 Greek,
CP1256 Arabic, Big5, Shift-JIS, GBK and EUC-KR. An exhaustive sweep of all
55,585 valid lead/trail byte pairs in the four legacy CJK encodings confirms no
double-byte character can be mistaken for a link.

UTF-16 subtitles are now explicitly left untouched. Links are not detected in
them, but nothing is damaged either.

**Documentation**

The README now documents "Remove Links from Subtitles" in full — what is
matched, why matching is conservative, and the encoding guarantees — and a new
in-app Help section explains the upload limits.

**Upload limit wording**

The limit counters said "50 per day", which read as "resets at midnight". The
windows are rolling, so they now say "50 of 50 in last 24h" and "in last 7 days",
and the counters make clear they count individual subtitle files.

## v1.9.0 - v1.9.0

*Released: 10/4/2026*

Version 1.9.0 - Remove links from subtitles

New opt-in option: **Settings → Processing → "Remove Links from Subtitles"**
(off by default). Implements #14.

When enabled, dropped subtitles are scanned for:

- URLs — `http(s)://`, `ftp://`, `magnet:`, bare domains, `www.` hosts
- Email addresses
- IPv4 addresses, with optional port and path
- Obfuscated links — `example (dot) com`, `example [.] com`,
  `www dot example dot com`, `hxxp://`
- Social handles — `@releasegroup`

Nothing is changed silently. A preview dialog lists every match with its
line number and category, shows a live before/after diff, and lets each
match be unchecked individually before anything is applied.

Matching is conservative, because subtitles are not clean prose:

- A dotted token counts as a domain only when its last label is a real
  delegated TLD, so `example.com` is stripped while `example.commute`
  is left alone.
- 107 TLDs are also common sentence-starting English words (`.it`, `.to`,
  `.me`, `.now`, `.one`). Subtitles frequently drop the space after a
  period, so those need a scheme, a `www.` prefix, or a path/port before
  they count as links — `"Stop.It's over"` and `"I know.Now go"` survive,
  `http://stop.it` and `stop.it/freesubs` do not.
- A Title-Cased TLD is treated as a sentence boundary; ALL-CAPS still
  matches, so `VISIT EXAMPLE.COM` is caught.

Subtitle structure is preserved. Timing lines, indexes, ASS headers and
MicroDVD frame markers are never touched. Cues left holding nothing but a
link are dropped and the remaining ones renumbered. Edits are applied over
a byte-preserving latin1 view, so cp1250/cp1251/Big5 files keep their
original encoding byte-for-byte.

The TLD list is generated from IANA via `npm run generate-tlds`.
Covered by 99 new unit tests.

## v1.8.22 - v1.8.22

*Released: 9/7/2026*

Version 1.8.22 - Session keep-alive and auth robustness

Keep the OpenSubtitles session alive while the app is open, and stop
transient network failures from logging users out.

The app stores a server-issued PHPSESSID as its session token. The server
expires it six hours after the last request (Set-Cookie Max-Age=21600),
and nothing was refreshing it.

Session keep-alive:
- Add XmlRpcService.noOperation() and an hourly keep-alive ping
- Ping is best-effort: it never mutates authentication state, because
  NoOperation answers 200 OK even for tokens the server never issued
- Guard against timer stacking, stale in-flight state, and hung sockets
